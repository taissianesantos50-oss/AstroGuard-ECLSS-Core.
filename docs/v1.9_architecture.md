# AstroGuard ECLSS Core v1.9 — Advanced Mission Health Analytics Architecture

Developer: **Taissiane Thais dos Santos**

Status: **development branch / research prototype**

## 1. Objective

v1.9 extends the stable v1.8 baseline with a deterministic analytics layer for synthetic mission-health telemetry. The implementation remains inspectable, low-resource and reproducible.

## 2. End-to-end pipeline

```text
Synthetic Mission Scenario
        |
        v
health_monitor.c / evaluate_health()
        |
        v
HealthTelemetry samples
        |
        +------------------------------+
        |                              |
        v                              v
telemetry_v1_9.csv          mission_health_analytics.c
                                       |
                                       v
                            MissionHealthAnalytics
                                       |
                                       v
                    mission_health_analytics_v1_9.csv
                                       |
                                       v
                            v1.9 Mission Dashboard
```

The dashboard presents the mission state, environmental variables, synthetic human telemetry, deterministic state counts, persistence metrics and the mission trend.

## 3. Core components

### `src/health_monitor.c` / `.h`
Classifies each synthetic physiological telemetry sample into `NORMAL`, `ATTENTION` or `CRITICAL` using explicit software rules.

### `src/mission_health_analytics.c` / `.h`
Aggregates a sequence of classified samples and computes:

- total sample count;
- counts of NORMAL, ATTENTION and CRITICAL samples;
- longest consecutive ATTENTION run;
- longest consecutive CRITICAL run;
- mean heart rate;
- mean SpO2;
- mean body temperature;
- mean respiratory rate;
- mean fatigue index;
- mean wellbeing index;
- deterministic mission trend: `STABLE`, `IMPROVING` or `DEGRADING`.

The current trend rule compares the severity class of the final sample with the first sample. It is intentionally simple and auditable; it is not a predictive model.

### `src/astroguard_v1_9.c`
Runs the deterministic synthetic verification scenario, records temporal telemetry, invokes the analytics module and exports both raw and aggregate outputs.

### `dashboard/`
Visualizes the synthetic scenario and the v1.9 analytics summary. The browser representation is a demonstration layer and does not replace the C analytics implementation as the verification reference.

## 4. Generated verification outputs

`telemetry_v1_9.csv`

Contains the time-series mission/environmental values, synthetic human-health values, actuator state and classified health status.

`mission_health_analytics_v1_9.csv`

Contains the aggregate deterministic mission-health summary generated by the C implementation.

These files are generated during execution and validated by CI; they are not evidence of real astronaut or clinical measurements.

## 5. Verification strategy

The GitHub Actions workflow performs:

1. compilation and execution of health-monitor unit tests;
2. compilation and execution of v1.9 analytics unit tests;
3. compilation and execution of the v1.4 baseline simulation;
4. verification of the baseline telemetry artifact;
5. compilation and execution of the integrated v1.9 simulation;
6. verification of `telemetry_v1_9.csv`;
7. verification of `mission_health_analytics_v1_9.csv`;
8. Python source syntax verification for the existing visualization layer.

The stable v1.8 baseline remains on `main` while v1.9 is developed and reviewed on `v1.9-advanced-mission-health-analytics`.

## 6. Safety and scientific boundary

AstroGuard v1.9 is a software research/simulation prototype. Human-health telemetry in the current verification scenario is synthetic.

The project does **not** claim:

- medical diagnosis or clinical decision support;
- medical-device validation;
- use of real astronaut physiological data;
- operational spacecraft control;
- flight qualification or certification;
- NASA, Artemis or other agency validation or endorsement.

## 7. Current verification state

The integrated C analytics/telemetry pipeline and dashboard changes are subject to the repository's automated CI before merge to `main`. A successful CI run demonstrates that the checked software scenario compiles and satisfies the encoded automated checks; it does not constitute operational, clinical or flight validation.
